# Ideas

These are ideas that we did not try, and some that are now done. Each one says what to do, why it can help, and how large the work is. The measurements are from [lessons.md](lessons.md) and the README. Section 10 of lessons.md tells what the performance work changed, and which ideas did not work.

Now the network takes 0.28 s for lodash, 0.71 s for three.min.js and 0.56 s for react-dom.development.js. Stage A is about two thirds of each. The best order for value against effort: idea 20 for three.min.js, then idea 11 (the longest line of three.min.js is in the first rounds, in the token run and at the end of stage A), then idea 7 (to show where the GPU wins), then idea 13 (to show that the result stays exact on more code).

## Quick changes (hours)

1. **Done: do not run captures in the speculation rounds.** The rounds use experts without captures, `pre`, capture slots and token registers. Only the final run makes tokens. A late round's step went from about 4 µs to 2.1 µs.
2. **Start the driver before stage A is complete.** Stage A runs in groups of 8,192 lines. Start round 1 on the lines of a group when that group is complete, instead of when all lines are complete. Now round 1 takes about 15 ms on lodash, so the gain is small.
3. **Keep the last rounds on the GPU.** After about round 10, a round runs only a few lines. On lodash, its cost is mostly fixed: a dispatch, a readback and a walk on the host, about 1 ms to 2 ms. A persistent kernel can run the last rounds and do the stitch on the GPU. On three.min.js, a late round waits for a line of about 1,500 steps, so the gain there is small. Since idea 17, there are only 9 to 14 rounds, so the gain is now small on all fixtures.
4. **Run the demo's work in a Web Worker.** Then the page does not stop for some seconds on the large files.
5. **Do less in each driver step.** Part of this is done: without tokens, a walk goes to `post` directly, and `post` finds the match's scope itself.
   - A search step can examine 4 positions instead of 1, from 4 record rows. On three.min.js, 96% of the search runs find a match at their first position, so the gain there is small. On lodash, half of the search runs are longer than one position.
   - The token experts are larger than the experts without tokens (the walk has 334 live operations, not 204). The token run of three.min.js waits about 45 ms for its longest line. Fewer operations there make that run shorter.
   - Measure each change on the GPU. A shorter chain of reads with more reads made the walk slower (lessons.md, section 10).

## Larger changes (days)

6. **Bit-parallel automata in stage A.** Now each node is a unit with its own list of items. For each automaton, keep the states as bits of 32-bit words. Then a step can be shift-and-mask operations on words, as handwired's `bit-emit.ts` does for its regex search. Phase 1 now starts from the nodes that hold (lessons.md, section 10), and is about 20% of stage A's throughput on lodash. So the gain is now smaller than it was.
7. **Many files in one run.** The GPU is fastest when it has much independent work. Highlight all the files of a repository together: stage A for all files, then rounds for all files at the same time. The fixed cost of a round then applies to many files. This is the most probable way to be clearly faster than shiki.
8. **Short lines as bit lanes.** lodash has 16K short lines, and each line pays the full cost of the barriers at each position. Let one workgroup do 32 lines at the same time, one line per bit lane. Then each barrier serves 32 times the work.
9. **Highlight again after an edit.** When an editor changes some lines, run stage A again only for those lines. Start the speculation from the stacks that are already known. It should then need only one or two rounds. The design fits this use well.
10. **A smaller record.** A record row is 200 words, and stage A writes about 430 MB for each fixture. Most of these words are ok bits for the walk. A smaller row means fewer writes, and lets a dispatch hold more lines. Without the record writes, stage A on lodash is about 5% faster.
11. **Speculation inside long lines.** Part of this is done, in the lite version only (idea 25): stage A runs long lines as chunks with overlaps, and the driver runs them as segments. The full version still runs a long line as one job. Divide the long lines of three.min.js into segments, and speculate on the state at the start of each segment, as for lines. The longest job then becomes shorter. The token merge between two segments needs care: the last token of a segment can merge with the first token of the next segment. The longest line (7,114 code points, about 9,000 steps) sets the time of rounds 1 to 3 and of the token run, about 110 ms together.
12. **The task levels of stage A.** Part of this is done: the lookahead start items are now in lists per class (85 of 1,011 for each class). Level 2 still has 510 guard predicates, and 370 of them are lookahead predicates. A pass from the lookaheads that hold was slower (lessons.md, section 10). Almost every guard list has at most one positive lookahead predicate, so no counters were necessary, but the pass needs an extra barrier. Anchor predicates are only 40, so a table per context for them gives little. Another form to try: one load for each entry, not two.

## Confidence and research

13. **Test more code.** Four files are a small test set. The React builds are now fixtures, and they are identical to shiki. Compare the network with shiki on more code: the TypeScript compiler's sources, JSX, test262, and random JavaScript from a fuzzer. Each difference shows a part of the semantics that the network does not copy, or a feature that the compiler does not accept.
14. **Other grammars and themes.** TypeScript and CSS will probably work. Markdown and HTML need injections, `while` rules and captures with patterns. This shows how general the compiler is.
15. **Done: stage A as a handwired circuit.** `src/net/stage-a-circuit.ts` builds the forward step and the backward step of stage A with handwired's `Circuit`. `pnpm check:stage-a-circuit` runs them with handwired's tensor evaluator and compares them with the dense CPU evaluation. On 30,590 positions of the four fixtures, with the long lines of three.min.js, there are 0 differences. Thus all of the network is handwired in the same sense. The backward step has 47,846 live operations in 12 layers, and it does all of them at each position. The GPU kernel does not run this circuit, because the kernel works only on the bits that hold (about 1% of the nodes). handwired's row writer can write the circuit as WGSL, but that kernel would be much slower.
   - The atomic group's integer end became two bits for each body node (lessons.md, section 5). The kernel can use the same bits. Then it does not read the record at the end of the group.
16. **Use the network as a model that can learn.** This is the purpose of handwired. Use the network as an exact front end, with fixed weights, for a model that learns. Or let its weights change, to learn a highlighter for a dialect that has no grammar.
17. **Done, with a simpler fix: predict a line only as far as its run agrees.** Alone, it took the rounds from 347 to 9 on react-dom.development.js, from 84 to 12 on lodash and from 64 to 14 on three.min.js (lessons.md, section 10). With idea 18, the rounds are 6, 10 and 14. A parallel prefix tree was not necessary. The analysis below is from before the fix.
   - The fix: the prediction for an invalid line took the effect of its best run, also the pops past the first frame where the run's prefix and the new start differ. Those pops came from frames that the new start does not have. Now the prediction pops only the frames that agree, and then pushes what the run pushed.
   - What is left: rounds 1 and 2 run every line, and each later round still fixes the lines after one wrong guess. Most wrong guesses are lines whose runs all started from a wrong top frame, for example a closer that ran only from the root. A prefix tree of line functions can still remove some of these rounds, but the rounds after round 2 now cost about 20 ms to 40 ms in all.
   - Before the fix: react-dom.development.js needed 347 rounds and lodash 84. The cause:
     - Round 1 runs every line from the root. From the root, a line that closes something does not pop: `  268435456;` that ends a multi-line `var X =`, or `  }` that ends a function. The openers still push. So the chain that round 2 predicts collects frames that are never popped, and many of its stacks are 64 frames deep.
     - After that, the chain past the frontier stayed wrong. A trace showed why: the prediction for an invalid line used the pops of a run from a wrong, deep start. For example, `      COMPARE_UNORDERED_FLAG = 2;` ran from a stack with extra `var` frames, and popped 6 frames, not 2. So each round fixed about one closer: one function, or one `var` group of three lines.
     - A test gave the stitch the most frequent prefixes that runs read (from the final result, so this is the best case), and ran every line from each of them in round 2. With 8 prefixes: 86 rounds, and the rounds and the stitch took 356 ms, not 479 ms. With 16 prefixes: 23 rounds, but 632 ms, because of 450K extra runs. So more candidate starts are not a good fix.
     - The proposal was a different algorithm. A line is a function of the frames that it reads: it pops k frames and pushes others. Compose these functions in a parallel prefix tree, about 15 levels for 30K lines. The difficult part is a line whose function has many cases, one for each set of frames that it can read.

## Duplicates, convergence and overlap

These ideas came from a second look at the code and the fixtures. Ideas 20 to 24 have only counts.

18. **Done: lines with the same text share their runs.** A run depends only on the line's text, the `firstLine` flag and the frames that it reads. So a run of one `  }` line is also a valid run for each other `  }` line with the same frames on top. Only 47% of lodash's lines are distinct, and 62% of react-dom's. `stitchLines` now keeps one trie of runs for each group of lines with the same text (line 0 stays alone). The best of 4 calls, alternating with the earlier version:

    | File | Rounds | Line runs | Driver |
    | --- | --- | --- | --- |
    | lodash | 84 → 20 | 56K → 31K | about 130 ms → 60 ms |
    | react-dom | 347 → 51 | 72K → 46K | about 380 ms → 130 ms |
    | react | 48 → 7 | 9.2K → 5.7K | about 50 ms → 19 ms |

19. **Done: stage A once for each distinct line.** A line's record depends only on its text, so stage A now runs once for each text, and a driver job reads the record of its line's text. The distinct lines are 68% of lodash's code points, 82% of react-dom's and 88% of react's. Stage A went from about 230 ms to 160 ms on lodash, and from about 500 ms to 400 ms on react-dom.
20. **Segments inside long lines for stage A.** Idea 11 divides long lines for the driver. Stage A has the same problem: three.min.js's stage A (about 0.6 s) ends with its longest line alone. Calculate each segment backward from a guessed state at its right end, for example the state after a short warm-up. When the true state from the next segment is known, calculate again from it, and stop when the new state is equal to the guessed run's state at the same position. From there, all earlier states are equal, because the step is deterministic. The states of regex automata usually become equal after a few positions. The forward pass of the lookbehinds can use the same method. For three.min.js, this is probably the largest gain.
21. **The token run during the last rounds.** After a round, every line before the first invalid line is final. Its token run can start with the next round, when the GPU is mostly idle. On three.min.js, the token run waits about 45 ms for the longest line. When that line becomes final early, its token run can go into an earlier dispatch.
22. **Copy the row in runs of one class.** Leading whitespace is 15% to 16% of the code points of lodash and the React builds. When the class and the context bits stay the same, and the state at p + 1 is equal to the state at p + 2, the state at p is equal to the state at p + 1. Then stage A can copy the row and not calculate it. The comparison must include the lookbehind bits. Count first how often the condition holds.
23. **Merge the nodes that have the same future.** `ok[c](p)` depends only on what follows c. Two nodes with the same class set and the same follow items (guard, target, marks, kind) have the same bits. A partition refinement, as in DFA minimization, can merge them. Most of the 19,765 nodes are lookahead internals, so probably some suffixes repeat. Fewer nodes make the record smaller (idea 10) and stage A faster. Count first how many nodes merge.
24. **Predict the stack after a closer from the indentation.** With vscode-textmate's stacks: after a closer line (it starts with `}`, `)` or `]`, with less indentation than the line before it), the next line's start is equal to the start of the last earlier line at the closer's indentation. This is true for 79% of the closers of react-dom and 93% of lodash's. The host can use that start as the prediction when a line's best run did not pop. The chain stays exact, because the check of validity does not change. It works together with idea 18. Since idea 17, only 6 to 14 rounds are left, so count first how many of them a closer causes.
25. **Done: the lite version.** `codeToTokens(code, {lite: true})` gives up exactness for time (README, "The lite version"). Stage A runs long lines as chunks of 512 positions, with 64 positions before and 128 after: this is idea 20 without the check of the guessed state. The driver runs lines longer than 192 code points as segments of about 128, which the host stitches as lines: this is idea 11 without the exact token merge. On all six fixtures, the output stayed identical to shiki. three.min.js went from about 0.86 s to 0.51 s, and scanner.ts from 0.67 s to 0.14 s. The lite option `maxRounds` stops the host's rounds early. It is not in the default (lessons.md, section 10). Next steps for the lite version:
   - **Fewer rounds for segments.** Segments made three.min.js need 107 rounds, not 64, because a segment's predicted start can be wrong as a line's can. A late round costs about 2 ms, most of it fixed. Idea 24 and a stitch that composes lines (idea 17) can help here too.
   - **Smaller overlaps.** Each chunk does 37% more work for its overlaps. On three.min.js, stage A is now limited by throughput, so smaller overlaps can help. Overlaps of 8 and 16 positions gave wrong tokens, so the gain is small.
